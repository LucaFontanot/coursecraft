# M24 Everyday speed and fewer clicks

Goal: make the things authors do every day faster: a quicker editor on big courses, lighter save and publish, rename in place, a faster publish-and-check loop, faster trigger and canvas work, a smaller web player, and a batch of small daily fixes. Based on Gemini 4 Neon's plan (`target/m24/neon-plan.md`), checked against the code and trimmed in review.

No step changes play-time behaviour or the course schema except two optional editor-only fields (`EditorSettings.last_publish`) with serde defaults. The published player must look and behave as before; step 6 only changes build settings, the order of two start-up fetches and early fetching of the next slide's pictures.

Clean-room: our own wording, layout and icons. Nothing here is near the patent watch list in `docs/contributing.md`.

Left for later (M25+): richer object states and button sets, master triggers, a variables manager, mobile player controls, web video layering, cross-course slide templates. Dropped from Neon's list: the web player console log (already off on the web), switching the web renderer to glow and removing egui's default fonts (too risky for the player), wasm-opt (needs a download).

## Step 1: Editor speed and lighter save and publish

Behaviour must stay exactly the same; this step only removes waste. Crates: coursecraft-ui-egui, coursecraft-publish, coursecraft-format, coursecraft (apps/coursecraft), coursecraft-cli.

1. **Slides panel clones every scene every frame.** `crates/ui-egui/src/slides.rs` about line 961, in `show_slides_content`: `let scenes = editor.session.course.scenes.clone();`. Replace it with a light per-frame list that copies only what the loop reads (scene id, title, slide ids and titles, whatever the loop body uses), or borrow and defer mutations to after the loop (the function already collects `scene_to_rename`, `bank_to_rename` etc. and acts after). Do not clone whole `Slide`s.
2. **Trigger editor clones the whole course every frame.** `crates/ui-egui/src/triggers.rs` about line 1976 in `show_trigger_editor_window`: `let course_clone = editor.session.course.clone();`. The form helpers (`render_action_fields`, `render_event_fields`, condition rendering) take `&Course` and `&Slide`. Take what they need without the full clone: e.g. temporarily `std::mem::take` the form state out of `editor.ui` so `&editor.session.course` can be borrowed while the form is drawn, then put it back. Leave line 1913 (`trial` clone on Save) alone; it runs once per click.
3. **Properties panel clones lists every frame.** `crates/ui-egui/src/properties.rs` about lines 5368–5410: `system_fonts.clone()`, `media_names` collect, slide `(id, title)` collect. Cache them in a small struct on the editor UI state keyed by `editor.session.revision` (and the media count / font-list length), rebuilt only when the key changes. Same for `media_references(&editor.session.course)` in `crates/ui-egui/src/media_library.rs` line 128 (the per-frame one; leave the ones that run on a button click).
4. **Course check on every edit.** `crates/ui-egui/src/lib.rs` about line 3106 calls `refresh_validation()` (runs `course.validate` and `course.audit`) on every revision change. Keep `course.validate` on every change, but run `course.audit` only after edits have been quiet for 300 ms (use the egui input time, `ctx.input(|i| i.time)`, and `request_repaint_after` so it does run), and immediately when the Accessibility/Validation panel or the Publish dialog opens (`publish.rs` line 146 already calls `refresh_validation`; keep it running both). Split the function into `refresh_validation()` (both, now) and a deferred audit; existing tests that call `refresh_validation()` must still see both results.
5. **Save copies the whole project in RAM.** `apps/coursecraft/src/files.rs` line 126 builds the full `.ccraft` with `save_project` into a `Vec<u8>` and then writes it. `crates/format/src/lib.rs` line 219 has `save_project_to<W: Write + Seek>`. Stream into the temp file instead (keep the existing write-to-temp-then-rename safety exactly as it is).
6. **Publish copies every media file twice.** `apps/coursecraft/src/main.rs` lines about 1471, 1580 and 1637 do `bytes.to_vec()` for every media file on the UI thread before spawning publish. Editor media is `Arc<[u8]>`-like (check the type of `editor.media`); pass the shared handles (`Arc<[u8]>` clones are cheap) into the publish job in `apps/coursecraft/src/publish.rs` instead of `Vec<u8>`. In `crates/publish/src/lib.rs`, change `PackageFile.bytes` from `Vec<u8>` to `std::sync::Arc<[u8]>` only if that stays small; otherwise keep `PackageFile` and just remove the UI-thread copy. Update every caller the compiler points to (CLI, tests). Published zips must be byte-identical to before (an existing publish test compares output; it must pass unchanged).
7. **Tests.** A ui-egui test that runs 10 idle frames with the trigger editor open and asserts no full-course clone path is taken (add a counter in `guard_counters.rs` if needed); a test that 10 quick edits run the audit once after the quiet time, not 10 times; a format test that a project saved with `save_project_to` reopens equal to the original.

## Step 2: Inline rename and timeline in seconds

Crates: coursecraft-ui-egui (and coursecraft-engine only if a rename command is missing).

1. **Rename a slide in place.** In the slides panel (`crates/ui-egui/src/slides.rs`), double-clicking a slide's title under its thumbnail opens an inline text field; Enter or clicking away saves, Esc cancels; an empty title is not saved. Reuse the existing pattern for scenes and masters: `SceneRename`, `start_master_rename` (about line 446) and `show_master_rename_editor` (about line 461), which run `slide.set_title` (check the exact command id there). Also add "Rename" to the slide right-click menu (`show_slide_menu_items`, about line 654) and F2 when the slides panel has focus and one slide is selected.
2. **Rename an object on the timeline in place.** In `crates/ui-egui/src/timeline.rs`, double-clicking an object's name in the timeline's left column opens an inline field, same keys as above, saving through the existing object rename command (grep `object.rename` or `set_name` in `crates/engine/src/commands.rs`). The timeline already has inline cue rename (`CueRename`, `SlideCueRename` about lines 95–152); follow that pattern.
3. **Seconds, not ms.** The timeline duration field (about lines 436–441 of `timeline.rs`) shows raw milliseconds. Show and edit it in seconds with one decimal and an "s" suffix (e.g. `5.0 s`), stored as ms as today. Same for any other duration the timeline panel shows in ms.
4. **Tests** (new module `rename_tests.rs`): double-click a slide title, type a name, press Enter, the slide title changed and Undo restores it; Esc cancels; empty name is ignored; timeline object rename works and undoes; the duration field shows `5.0 s` for 5000 ms and typing `2.5` stores 2500.

## Step 3: Faster publish loop and Open in browser

Crates: coursecraft-ui-egui, coursecraft (apps/coursecraft). Desktop only where noted; the web editor must still compile (`cargo check -p coursecraft-ui-egui --target wasm32-unknown-unknown`).

1. **Remember the last publish settings.** `crates/ui-egui/src/publish.rs` (`open_publish_dialog` about line 137, `show_publish_dialog` about line 187): the dialog opens with the standard (SCORM 1.2 / 2004 / xAPI / cmi5 / LTI / Web) and other options chosen last time for this course. Store them in the course's editor settings (`Course.editor: EditorSettings` from M23, `crates/course/src/model.rs`; add an optional `last_publish` field with serde default, skipped when None) so they survive save and reopen. Save them through an engine command when Publish is pressed (grep how M23 saves `EditorSettings`, e.g. guides, and do the same; an ordinary undoable edit is fine). Keep this simple.
2. **Publish finishes instantly.** `apps/coursecraft/src/main.rs` about line 1512 polls the publish thread with `request_repaint_after(from_secs(1))`. Give the publish thread a clone of `egui::Context` and call `ctx.request_repaint()` right after it sends the result. Keep the 1 s poll as a fallback.
3. **Open in browser (desktop).** After a successful publish, the success area shows an "Open in browser" button. It starts a tiny local web server in a new file `apps/coursecraft/src/preview_server.rs` using only `std::net::TcpListener` (no new dependencies): bind `127.0.0.1:0`, serve the files of the just-published zip from memory (read it with the `zip` crate already used in the workspace), GET only, `/` maps to `index.html`, reject paths with `..`, correct `Content-Type` for html, js, wasm (`application/wasm`), json, css, png, jpg, svg, webp, mp3, mp4, vtt, xml; unknown types `application/octet-stream`. One background thread, a new server replaces the old one, it stops when the app quits. Then open `http://127.0.0.1:<port>/` with the system opener (`open` on macOS, `xdg-open` on Linux, `cmd /C start` on Windows) via `std::process::Command`. For SCORM/xAPI/cmi5 packages the player runs without an LMS, which is fine for a preview; label the button "Open in browser (preview, no LMS)" for those and "Open in browser" for Web. No `unwrap`; every error becomes a status message.
4. **Tests:** ui-egui test that the dialog reopens with the last standard chosen; a unit test for the server's path-to-file and content-type logic (pure functions, no sockets), including `..` rejection; a test that starts the server on a small in-memory zip, fetches `/` and `/a.wasm` with `std::net::TcpStream`, and checks status and content type.

## Step 4: Faster trigger authoring

Crate: coursecraft-ui-egui only (`crates/ui-egui/src/triggers.rs`). No change to what triggers do at play time.

1. **Selected object by default.** When the author adds a trigger while an object is selected on the canvas, the new trigger's event object (e.g. "user clicks") defaults to that object instead of the first object on the slide. Find where a new `TriggerFormState` is created (grep `TriggerFormState::` / `new_trigger`).
2. **Double-click to edit.** Double-clicking a trigger row in the triggers tab (`show_triggers_tab`, about line 1471) opens it in the trigger editor, same as its Edit button.
3. **Keys in the trigger editor** (`show_trigger_editor_window`, about line 1961): Esc closes without saving (only when no combo box or text field popup is open), Cmd/Ctrl+Enter saves (same as the Save button, including its validation).
4. **Filter and group.** Above the trigger list, a small filter box that narrows the list by the plain-words description text (case-insensitive), and a toggle "Group by object" that groups slide triggers under their event object's name. The selected canvas object's triggers are shown first when the toggle is off.
5. **Reorder.** Up/down arrow buttons on the selected row (or drag, if the list already supports drag elsewhere) that move a trigger within its list through the existing engine reorder command (grep `trigger.move` / `reorder` in `crates/engine/src/commands.rs`; if none exists, add `trigger.move` with `{slide, layer?, from, to}` and an engine test; trigger order matters at play time, so this is a normal undoable edit).
6. **Tests** (`trigger_speed_tests.rs`): new trigger defaults to the selected object; double-click opens the editor; Esc closes without change; Cmd+Enter saves; the filter hides non-matching rows; moving a trigger down changes order and Undo restores it.

## Step 5: Faster canvas work and editing many objects at once

Crates: coursecraft-ui-egui (and coursecraft-engine only if a needed batch command is missing).

1. **Alt-drag duplicates.** In `crates/ui-egui/src/canvas.rs`, starting a move-drag with Alt (Option) held duplicates the selected objects and drags the copies, leaving the originals in place, as one undo step. Find the drag start (grep `CanvasDrag` and the `alt` reads around lines 2322, 3172, 4663; make sure Alt isn't already used for something else at drag start — if it is, tell me and skip this item).
2. **Shift keeps one axis.** Holding Shift during a move-drag locks movement to the axis with the larger movement so far. `compute_drag_frame` (about line 858) already takes `shift` for resize; apply axis lock to moves only.
3. **Space-drag pans.** Holding Space and dragging on the canvas pans the view (and middle-mouse drag does the same), without selecting or moving objects, and not while a text box is being edited (Space must still type a space then). Grep how the canvas pans/scrolls today.
4. **Cmd+B / Cmd+I / Cmd+U while typing.** While editing text on the canvas (grep the in-place text edit, around line 4471), these toggle bold / italic / underline on the selected text range (or the typing style when nothing is selected), through the same commands the Format panel's B/I/U buttons use.
5. **Multi-select editing.** In `crates/ui-egui/src/properties.rs`, when several objects are selected, the panel can also set animation (entrance/exit), outline, opacity and font for all of them in one undo step, the same way multi-select fill works today.
6. **Bug: multi-select Button fill wipes the gradient.** `properties.rs` about lines 2323–2334 rebuilds a bare `{type, label, fill}` JSON for buttons; patch the existing kind instead (`serde_json::to_value(&object.kind)` and change only `fill`), as the Shape branch does, so `fill_style` and other fields survive.
7. **Tests** (`canvas_speed_tests.rs`): Alt-drag leaves the original and adds a copy at the new spot, one Undo removes the copy; Shift-drag of (40, 5) moves only on x; Space-drag pans and doesn't move the selection; Cmd+B during text edit makes the selection bold; multi-select opacity sets both objects; multi-select button fill keeps an existing gradient `fill_style`.

## Step 6: Smaller, faster web player (do NOT change what the player does)

Crates: coursecraft-player (apps/coursecraft-player), xtask. The published player must look and behave exactly as before. Do not change renderer (keep wgpu), do not touch fonts or egui features, do not change `crates/logic` or `crates/render`. If something here would need that, skip it and say so.

1. **Smaller wasm build.** Add a Cargo profile `[profile.wasm-release]` in the root `Cargo.toml` that inherits `release` with `opt-level = "z"`, `lto = "fat"`, `codegen-units = 1`, `strip = true` (leave `panic` as it is). Make trunk use it for the player: in `apps/coursecraft-player/index.html` add `data-cargo-profile="wasm-release"` to the `<link data-trunk rel="rust" ...>` tag (trunk 0.22 supports it; if `trunk build --release` rejects it, use `--cargo-profile wasm-release` in `xtask` `build_player` and `package_example` instead). Do not add `data-wasm-opt` (it downloads a tool; the network is off).
2. **No demo course in the player bundle.** `index.html` copies `examples/hello-course/course.json` into the dist for local `trunk serve`. Keep that line (local dev needs it), but in `xtask/src/main.rs` `build_player` (about line 312), after a successful build, delete `course.json` from the dist folder so it isn't embedded in desktop builds or published zips. Check that publish writes its own `course.json` (it does in `crates/publish/src/lib.rs`), so nothing else depended on the copy; grep `player-dist` and `player_bundle` to confirm.
3. **Start-up fetches together.** `apps/coursecraft-player/src/load.rs` (about lines 250–301) fetches `course.json`, then `coursecraft-package.json`. Start both requests at once and continue when both have answered, with the same error handling and the same result as today (a missing package file still means the same default it means now). Keep the `ehttp::Credentials::SameOrigin` setting on both requests exactly as it is (that fixed SCORM Cloud).
4. **Load the next slide's pictures early.** In `apps/coursecraft-player/src/media.rs`, after the current slide's media has loaded, start fetching the images (not video) of the slide that "Next" would go to, if not already fetched. Only fetch; don't decode early or change drawing. Cap: if the web media cache holds more than 128 MB of raw bytes, drop the least recently used entries that aren't on the current slide.
5. **Measure.** Add the raw and gzip size of the built `_bg.wasm` to the report written by `cargo xtask perf` if that command already writes a report (grep `fn perf` in xtask); otherwise print it at the end of `build_player`. Do not run a release build yourself; I will.
6. **Tests:** a player unit test for the both-fetches-together logic (the pure part: combining two results into the start-up state, including the missing-package case); a test for the LRU cap with fake entries; an xtask unit test, if easy, that the dist cleanup removes `course.json` and nothing else. Check with `cargo test -p coursecraft-player -j 4`, `cargo clippy -p coursecraft-player --all-targets -j 4 -- -D warnings` and `cargo check -p coursecraft-player --target wasm32-unknown-unknown`.
